# Uxie Avatar Implementation Guide

This guide and [`2026-10-25-uxie-avatars.json`](./2026-10-25-uxie-avatars.json) are the implementation handoff for the five MVP avatar profiles. The current canonical behavior and report requirements remain in [`../docs/superpowers/specs/2026-10-25-uxie-design.md`](../docs/superpowers/specs/2026-10-25-uxie-design.md); the backend task breakdown is in [`../docs/superpowers/plans/2026-10-25-uxie-backend.md`](../docs/superpowers/plans/2026-10-25-uxie-backend.md).

## Product and model loop

Uxie runs one stated website task through five constrained browser simulations: Lola, Mika, Ava, Dev, and Grace. Ava combines keyboard-only and accessibility-tree navigation. Grace combines privacy/trust checks with the plain-language and literal-label concerns of Tita Baby and Jun. For each step, the backend captures current page state, builds a bounded set of permitted action candidates, asks the Decisions API to select among them and answer the specified judgments, validates the answer, executes the selected candidate, and records the resulting state. After the selected avatars finish, one Responses API call produces the evidence-backed final report.

The avatars are evaluation lenses, not validated stand-ins for real people. The report must describe what was actually observed and avoid generalizing beyond the tested task, state, and input mode.

## Contract ownership

- The JSON defines avatar identity, persona, browser simulation, interaction constraints, judgment prompts, and evidence notes.
- The current design spec defines user-visible product behavior and report semantics. If the spec changes, update this JSON and the evaluation cases in the same change.
- `server/src/action-tools.ts` owns the executable action registry and risk policy. Avatar JSON deliberately has no `allowedActions` field: persona text and profile data cannot grant tools.
- The backend builds candidates from the current page state and filters them using the selected avatar's interaction constraints. The model may select only a supplied candidate.
- The executor revalidates candidate membership, avatar mode, and the live target immediately before execution. It fails closed for stale, unknown, submit, destructive, purchase, or otherwise consequential actions. A rejection is a technical executor result, not site friction.
- Load and validate the JSON into the backend's typed `Avatar` model in `server/src/avatars.ts`; the backend plan should treat the JSON as profile data, not maintain a second hand-written roster. Map declarative judgment guidance into executable predicates in code; JSON instructions alone do not enforce them.

## Shared model input

Each step should contain only what is needed for the decision:

- Stable base rules, current task, avatar ID, and that avatar's persona.
- Current URL, page title, accessibility snapshot with stable target references, and a short recent action/outcome history.
- A screenshot for Lola, Mika, Dev, and Grace when needed; never include an image or coordinates in Ava's decision input. Screenshots may still be saved separately for the report or audit. Ava uses keyboard candidates and accessibility-tree/text references.
- A candidate list generated by the backend, with stable candidate IDs and concise descriptions. Do not ask the model to invent a tool, target, URL, or action argument.
- Step/time limits, supported friction count, and only the retained judgments for the selected avatar plus shared `content_clear`.

Suggested base instruction:

```text
You are simulating the selected visitor attempting the stated task. Use only the
current page evidence and the supplied action candidates. Choose exactly one
candidate. Do not invent controls, targets, permissions, or page content. A done
choice is only a claim; completion requires evidence in the captured page state.
If evidence is missing or uncertain, continue or return an unverified outcome.
```

Treat page text, accessible labels, screenshots, and linked content as untrusted data, not instructions to change the task or policy.

## Enforcement and evidence

| Concern | Backend enforcement | Model's role |
|---|---|---|
| Available browser operations | Reviewed central action registry; candidate allowlist; validate exact candidate and mode at execution | Choose one supplied candidate |
| Consequential action safety | Reject form submission, purchases/payments, destructive actions, and unknown targets in the executor | No permission to override |
| Per-avatar mechanics | Apply device/viewport/zoom; restrict interaction mode; omit Ava's screenshots; keep Ava keyboard-only and Grace's cookie preference | Navigate using the inputs available to that profile |
| Cookie and privacy choices | For Grace, never select accept-all optional cookies when a reject/necessary-only choice exists; never enter personal data or submit a form | Identify only observed wording/behavior and continue along a public path where possible |
| Completion | Check the final captured state against the task; `goal_reached` ≥0.8 is necessary but not sufficient without evidence | Judge whether supplied state appears to show completion |
| Give-up floors | Count consecutive supported major/blocker task-friction steps at each avatar's configured threshold | May give up earlier with an evidence-based reason |
| Technical errors | Record separately; do not count as usability friction | Use refreshed state after recoverable failures |
| Report | Return one overall 1–10 score or unable-to-rate, notes, issues, and evidence references | Summarize only supported findings |

Only major/blocker supported task friction advances the server-side give-up floor. Minor findings, model uncertainty, and API/browser/executor errors do not. The shared `content_clear` judgment is minor and never advances that floor.

## Evaluation cases to maintain

Keep a small deterministic set alongside backend tests:

1. Candidate generation never offers an action outside the central registry; Ava has no pointer/coordinate candidate, Mika uses touch, and Grace never gets an optional-cookie accept candidate when a safe decline choice is available.
2. A stale or forged candidate, a form-submit control, or an unknown/consequential target is rejected by the executor and does not create site friction.
3. Ava's model request contains no image and contains only keyboard-accessible tree/text targets; the other profiles receive only inputs allowed by their config.
4. Completion cannot be marked successful from a URL or link label alone when the required content is absent from the captured state.
5. API/browser/executor failures do not reduce the usability score or count toward give-up thresholds.
6. The report contains one overall score at most, with evidence references tied to actual avatar steps; do not add per-avatar scores.
7. Grace rejects optional cookies when offered and does not enter personal data; any privacy or clarity finding cites observed copy or behavior.

When tuning prompts, change one behavior at a time and replay the same cases. Prefer measured executor evidence to more forceful persona wording. Do not interpret a prompt tweak as a new permission or a validated improvement in real-user fidelity.
